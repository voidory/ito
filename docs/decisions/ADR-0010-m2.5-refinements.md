# ADR-0010: M2.5 refinements — explanatory pages, category master pages, and annotation-style storage (A13, A14, §14)

- Status: ACCEPTED (M2.5, FEAT-001..006)
- Spec references: §12.1 + acceptance A13 ("The Bump" develops into a page that
  connects further subjects); §12.2 + acceptance A14 ("each category has one
  master page … a category master page may connect to another category
  boundary"); §14 + §20 (annotation highlight styles; clean domain `captures`
  for the M3 whole-brain export/restore validation).
- Relationship to prior ADRs: ADR-0008 fixed the relationship DATA shape (the
  2-page edge reconciled with the N-endpoint hub) and ADR-0009 fixed the
  canvas + 3D view state. This ADR is ADDITIVE over BOTH: it adds three
  OPTIONAL, readonly record fields and one load-time migration, with
  SCHEMA_VERSION unchanged.

## Context

M2 shipped the concept network (ADR-0008/ADR-0009). Closing M2 and preparing
for M3 (Complete Backup, Recovery, and Validation) surfaced three refinements
that the M2 summary under-specified. Each must be delivered WITHOUT a schema
migration so existing persisted v1 brains keep loading (real migrations are M7
per ADR-0004 and MILESTONE-MATRIX §6):

1. A13 / §12.1 — a relationship hub ("The Bump") was reduced to a short string
   label (`setRelationshipLabel`). The spec requires the short connection
   explanation to be able to DEVELOP into a full page that can connect further
   subjects, i.e. a real first-class `Page` endpoint, not an unnamed edge or a
   fixed-length label.
2. A14 / §12.2 — category-to-category links were derived SOLELY from a member
   relationship bridging two categories. The spec requires each category to
   have one MASTER page (a real editable `Page`) whose connection to another
   category's master page/boundary is a first-class capability, not merely a
   filter plus a member-bridging side effect.
3. §14 / §20 — M1 smuggled custom annotation highlight styles (`color`,
   `kind`, `strokeWidth`) into `BrainData.captures` via a sentinel `Capture`
   whose `sourceId === null`. This pollutes the domain `captures` array and
   would corrupt the M3 whole-brain export/restore validation, which expects
   `captures` to contain ONLY real user captures.

## Decision

### 1. `Relationship.explanatoryPageId?: PageId` — "The Bump" develops into a real Page (A13, §12.1)

We add an OPTIONAL, readonly `explanatoryPageId?: PageId` to `Relationship`.

- `Workbench.developRelationshipPage(relId): Promise<PageId>` lazily creates
  (or returns the existing) full subject `Page`, links it via
  `explanatoryPageId`, seeds its title from the relationship's label, and opens
  it in the `SubjectEditor` (ProseMirror). It is IDEMPOTENT: a second call
  returns the same page and creates nothing new.
- Because the explanatory page has a real `PageId`, it participates as an
  endpoint in FURTHER `Relationship` records through the SAME
  `relationshipEndpoints(rel)` normalizer from ADR-0008 — a connection can
  connect to further subjects with no special-casing.
- The short-label path is KEPT: in `NodesCanvas` the hub (`graph-hub`) still
  edits its short label inline via the prompt, and a distinct
  `open-connecting-page` control develops/opens the full page. The two are
  complementary, not mutually exclusive.

A relationship with no explanatory page is the degenerate case; nothing reads a
missing field.

### 2. `Category.masterPageId?: PageId` — each category has one master page that may connect another category's boundary (A14, §12.2)

We add an OPTIONAL, readonly `masterPageId?: PageId` to `Category`.

- `Workbench.getOrCreateCategoryMasterPage(categoryId): Promise<PageId>`
  lazily creates (or returns) a real subject `Page` seeded from the category
  name and records it on `masterPageId`. The master page is a first-class,
  `SubjectEditor`-editable `Page`.
- `Workbench.connectCategoryBoundaries(from, to): Promise<RelationshipId>`
  ensures BOTH categories have a master page and creates a `Relationship`
  joining the two master page ids — the explicit "a category master page may
  connect to another category boundary" capability.
- `deriveCategoryLinks` in `src/network/scene.ts` now emits
  `SceneCategoryLink.linkKind: "master" | "member"` and the 2D canvas renders
  `<line data-testid="category-link" data-link-kind="master|member">`:
  - a MASTER link is derived first, when a relationship directly connects one
    category's master page to another's master page (§12.2 capability);
  - a MEMBER link is retained as a SECONDARY signal — a relationship bridging a
    member page of each category — and is SKIPPED when a master link already
    covers the same unordered category pair (master wins the per-pair dedupe).
- 3D parity: `threeScene.map.ts` surfaces `Scene3D.categoryLinks` from the SAME
  derived scene so the 2D and 3D views stay in lockstep (the ADR-0009 parity
  rule).

When no master pages exist the output is exactly the legacy member-bridging
set (all `member`), preserving prior behaviour.

### 3. `PresentationState.annotationStyles?` — annotation styles leave `captures`; the sentinel is migrated away (§14, §20)

We add an OPTIONAL, readonly
`annotationStyles?: Readonly<Record<string, AnnotationStyleRecord>>` to
`PresentationState`, and `createEmptyBrainData()` seeds `annotationStyles: {}`
in the ONE place a `BrainData` is assembled (`src/model/brain.ts`).

- `Workbench.setAnnotationStyle` / `annotationStyle` now read and write SOLELY
  from `presentation.annotationStyles`. The M1 `readStyles`/`writeStyles`
  sentinel path (a reserved `Capture` with `sourceId === null` and a tagged
  text payload) is gone.
- A ONE-TIME load migration strips any legacy sentinel `Capture` records
  (`sourceId === null` carrying the style tag) out of `BrainData.captures` on
  open, so `captures` strictly contains real user captures. This is a data
  CLEANUP, not a schema version bump: the migration is lossless for style data
  (styles move to `annotationStyles`) and all existing M1 highlight-style tests
  stay green.

## Why this needs no migration

Every added field (`explanatoryPageId`, `masterPageId`, `annotationStyles`) is
OPTIONAL and readonly, so a persisted v1 `Relationship`, `Category`, and
`PresentationState` are each legal values of the refined type and read with no
code touching a missing field. `createEmptyBrainData()` seeds the sane empty
default (`annotationStyles: {}`). The sentinel strip runs on load and only
REMOVES the fake records M1 wrote; it never needs to UPGRADE a field shape.
Because nothing required changed, SCHEMA_VERSION remains `1`; version bumps +
real migrations are deferred to M7 (ADR-0004).

## Consequences

- "The Bump" is now a real node in the making: a connection can carry its own
  document and connect onward, which the ADR-0008 OPEN question anticipated.
- Category-to-category connection is a first-class, data-driven capability
  (master link) with the old member-bridging retained as a secondary signal;
  the lens/star and link-kind distinctions remain DERIVED, never stored as
  flags, so they cannot drift.
- `BrainData.captures` is clean for the M3 whole-brain export/restore
  validation; annotation styles live in presentation state where they belong.
- All additions are back-compatible (verified: full Vitest suite + typecheck +
  build green; the e2e specs enumerate/compile).

## OPEN

- Whether a category master page should auto-join the category's
  `memberPageIds` (so its squircle always frames it) vs staying a boundary-only
  node is an M5 layout-tuning question; today the master page is a real Page
  referenced by `masterPageId` and member pages drive the squircle bounds.
- Whether `annotationStyles` should be keyed per-source vs global (so the same
  highlight color scheme can differ per paper) is deferred; today it is a
  global style map, matching the M1 behaviour it replaces.
